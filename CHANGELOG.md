# Історія змін

## 2026-06-30 — Централізований SmartID із вибором розміщення (Kuber/IIS)

- SmartID тепер **один центральний сервіс SSO** на всю систему, розмір — від загальної к-сті
  користувачів. Окремі `SmartID` (Web) / `LMS-SmartID` / `HR-SmartID` прибрано (усуває роздування,
  коли SmartID масштабувався від тисяч облікових записів LMS/HR).
- У **гібриді** додано вибір розміщення SmartID: **Kubernetes** (под) або **веб-сервери (IIS)**
  (без окремої ВМ — IIS і є веб-сервер). У чистому K8s SmartID завжди под, у чистому Windows —
  на веб-серверах IIS. Перемикач показується лише в гібриді.

## 2026-06-30 — Картки середовищ, ForceBPM за розгортанням, версія SQL, назви з еталона

### Налаштування середовищ — картки
- Блок «Додаткові середовища» перероблено: кожне ввімкнене середовище (DEV/TEST/PreProd) —
  окрема **картка** з к-стю користувачів, модулями та опціональними вузлами; вимкнені не показуються.
- Поле к-сті модуля в картці — обрамлене (видно, що редагується), як поле «Користувачів» угорі.

### ForceBPM — керується типом розгортання
- ForceBPM (Kubernetes-only) тепер **без поля к-сті** (масштабується від загальної к-сті) і з
  **заблокованою галочкою**: Kubernetes/Гібрид — увімкнено, Windows — вимкнено (автоматично).
  K8s-сервіси завжди на Ubuntu-вузлах; на чистому Windows ForceBPM немає.

### Версія SQL
- Підпис вузла БД: **MS SQL Server 2025 (мін. 2022)** (рекомендовано 2025, мінімум 2022 — за
  D-AD-ADM-E 2025-10; апаратні вимоги між версіями не відрізняються).

### Назви сервісів — з еталонних розрахунків
- Прибрано самочинні переклади компонентів. Назви беруться дослівно з файлів розрахунків:
  `AS (Сервер додатків)`, `ROBOT (Планувальник)`, `Webrmd (Веб клієнт)`, а решта — канонічні
  технічні (`AS-Local SQL`, `ForceBPM Engine`, `WebAppModeler` …). Вузли — `Master node`, `Worker-node`.

### Звіт
- На вкладці «Підсумок» довга назва (напр. «… Гібрид (K8s + Windows)») більше не обрізається.

## 2026-06-30 — Розділення ВМ по середовищах у звіті, HA для HAProxy, pagefile БД

### Звіт Excel — аркуш «ВМ по середовищах»
- Замість однієї суцільної таблиці кожне середовище (PROD/PreProd/TEST/DEV) тепер **окремий
  блок-таблиця**: синій підпис із кількістю користувачів → шапка → рядки ВМ → підсумок «Разом» →
  рамка + відступ між блоками. Стиль узгоджено з аркушем «Інфраструктура».
- Колонку «Середовище» прибрано з рядків (вона у підписі блоку) — таблиця компактніша.

### HAProxy — відмовостійкість (High Availability)
- Додано опцію **«HAProxy HA (2 вузли)»**: балансувальник більше не мусить бути єдиною точкою
  відмови. У режимі HA додаються **2 вузли active/passive** (keepalived/VRRP, спільний VIP)
  замість одного, з відповідною приміткою у вузлі.
- Для PROD — чекбокс біля HAProxy (активний лише коли HAProxy увімкнено); для DEV/TEST/PreProd —
  окремий рядок «HAProxy HA (2 вузли)» у сітці «Додаткові вузли по середовищах» (керується незалежно).
- Залізо HAProxy лишається 2 ядра / 4 ГБ — для підтримуваних обсягів цього достатньо; масштабується
  лише кількість вузлів, а не специфікація.

### Файл підкачки (page file) сервера БД
- Прибрано фолбек, що нав'язував вузлу БД на Windows/Hybrid pagefile, рівний обсягу RAM. Виділений
  SQL Server не потребує pagefile, масштабованого від RAM (документ D-AD-ADM-E / еталонний калькулятор
  задають pagefile лише для серверів додатків/веб). Тепер усі режими (K8s/Windows/Hybrid) узгоджені —
  для вузла БД pagefile не показується.

## 2026-06-24 — Бекап від обсягу даних БД, версія/редакція СУБД, IOPS по вузлах, звірка з документом

### Бекап і диски БД
- Резерв під бекап тепер рахується від **обсягу реляційних даних БД** (нове поле «Обсяг даних БД, ГБ»),
  а не від усього виділеного диска. Усунено роздуття (раніше DEV/TEST сягали 4 ТБ під базу в 10 ГБ).
- Бекап-резерв додається до **кожного** середовища, включно з PROD (раніше — лише DEV/TEST).
- У Windows-розгортанні примітка зазначає ширший склад бекапу (БД + веб/клієнт/мережева), у Linux — лише БД.
- Диски `Data`/`Logs+TempDB` вузла БД масштабуються за обсягом даних (з розумними мінімумами) —
  немає терабайтних дисків під малу базу.

### СУБД
- У таблиці інфраструктури та звітах виводиться **версія/редакція СУБД** (MS SQL Server 2022,
  PostgreSQL 17+, Oracle 19c). Мінімальна версія SQL — 2022.
- Якщо рекомендований обсяг ОЗП SQL **> 128 ГБ** → автоматично редакція **Enterprise** (ліміт Standard),
  з відповідною приміткою.

### IOPS, ВМ, звіт
- «Всього IOPS» більше не сумується між дисками/вузлами — показник = IOPS **вузла БД** (визначальний),
  а IOPS кожного вузла лишаються в таблиці по вузлах.
- KPI/заголовки «Вузли» → «ВМ (серверів)».
- На вкладці результатів додано **прокрутку** (ScrollViewer).
- Розбивка **ВМ для кожного середовища** (PROD/DEV/TEST/PreProd) — в UI, HTML та Excel.
- Додано **звірку розрахунку з вимогами документа** D-AD-ADM-E (сервер БД: CPU/RAM/IOPS/затримка)
  з підсвічуванням відхилень — в UI, HTML, Excel, XML.
- Назву звіту узгоджено зі складом (користувачі + тип розгортання).

## 2026-06-18 — Узгодження «Всього vCPU/RAM» + документування формул реплік

### «Всього vCPU/RAM» — єдина основа для всіх режимів
- Підсумкові `TotalCpu` / `TotalRamGb` тепер означають **фізичні ресурси всіх вузлів**
  (`Σ вузол.Cpu × кількість`) однаково для K8s, Windows і Hybrid.
- Раніше K8s показував суму **запитів подів** (напр. 25.85 на 100 користувачів), що занижувало
  фізичний слід і було несумісним з Windows (фізичні ядра ВМ). Тепер K8s 100 користувачів →
  44 vCPU (SQL 8 + Master 4 + Worker 8×4), зіставно з Windows (20).
- Запит подів і далі використовується внутрішньо для розрахунку кількості worker-вузлів.
- Hybrid: підсумок рахується з фінального списку вузлів (після дедуплікації спільної БД) —
  усунено подвійний облік SQL-вузла.
- Для наочності додано окрему величину **«запит подів K8s»** (`PodCpu`/`PodRamGb`) — показується
  на вкладці результатів та у звітах TXT/HTML поряд із фізичним підсумком, щоб різниця між
  «скільки просять поди» і «скільки заліза провіжинимо» була зрозумілою. Для Windows = 0.

### Формули реплік — свідома калібровка (не змінено)
- Поди `ROBOT`, `WS (Веб сервіси)`, `ForceBPM Engine`, `HR Portal (SmartID/GraphQL)` масштабуються
  за каліброваними формулами, а не за загальним правилом «крок 25». Це навмисне інженерне рішення:
  фонові служби й рушії не масштабуються лінійно з користувачами (інакше — десятки зайвих реплік),
  а «фікс=1» недостатньо на великих обсягах. Більшість подів масштабуються рівно «крок 25» (за Excel).

## 2026-06-18 — Аудит: коректність, безпека, чистка репозиторію

### Виправлено
- **Підрахунок дисків.** Сумарний обсяг сховища (`TotalStorageGb`) тепер враховує розділені диски
  вузла (OS / Logs+TempDB / Data / Content), а не лише перший диск. Виправлено в рушії сайзингу,
  підсумку результатів та оцінці вартості.
- **XSS в експорті.** Назви вузлів і компонентів (походять з імпортованого Excel) тепер екрануються
  в HTML- та SVG-звітах.
- **Невалідний Terraform.** Генератор тепер створює `azurerm_subnet` та `azurerm_network_interface`
  замість посилання на неіснуючий ресурс; додано `source_image_reference`.
- **Ідентифікатори IaC.** Введено єдиний хелпер `SanitizeResourceName` — некоректні символи у назвах
  вузлів (пробіли, дужки, слеші) більше не потрапляють в ідентифікатори Terraform/ARM/Bicep/Pulumi.
- **Секрети в K8s-маніфестах.** Креденшали виносяться в `Secret` і підключаються через `secretKeyRef`,
  а не зберігаються у відкритому `env.value`.
- **Глобальний обробник винятків.** Непередбачені помилки більше не аварійно завершують застосунок.
- **Аліасинг матриці.** `CopyMatrix` робить глибоке копіювання — редагування грідів не мутує спільний стан.
- **Дрібниці.** Обмеження кількості користувачів (1–5000); тип СУБД враховується у профілі порівняння;
  усунено повторні підписки на події у вкладці калькулятора; прибрано дублювання логіки реплік та виклику `GetConfig`.
